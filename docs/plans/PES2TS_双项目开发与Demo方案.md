# PES2TS 双项目开发方案：先形成可复核的 Demo

> v2.0 · 2026-09-29。本文是当前项目定位与实施顺序的主方案；[旧版逐步实施与验证方案](PES2TS_逐步实施与验证方案.md)保留为历史记录。[首轮 24 条反应及复核规则](../demo/PES2TS_demo24_反应挑选与复核方案.md)和 [G1 v2 补全实施总方案](../design/G1_v2_补全实施总方案.md)分别给出样本与扫描计划细节。

## 1. 一句话定位与边界

结合 ACP 数据与任务要求的后续实施顺序，统一见 [PES2TS 统一开发顺序与阶段验收](PES2TS_统一开发顺序与阶段验收.md)；数据字段与对接细节见 [数据规范与 ACP 对接优化方案](../contracts/PES2TS_数据规范与ACP对接优化方案.md)。本文继续规定双项目职责、实验和评价边界。

**PES2TS = PES generation + PES ranking。** 前者从反应物/产物端点生成可审计的廉价近似反应路径及沿路径能量剖面；后者在**已经计算的路径**中筛选、排序可提交给过渡态优化的真实几何帧。两者通过稳定的 `PathBundle` 合同连接，可以分别开发、分别替换、分别评价。二者合并后，才是 PES2TS 的初猜交付流程。

这里的“PES generation”是项目名，不声称重建完整多维势能面；“PES ranking”首先是路径质量判断和帧排序，也不声称直接生成精确 TS。**成功终点**是从 R/P 输入出发，以固定预算得到 OptTS 收敛、频率分析确认目标反应模态的一阶鞍点、双向 IRC 连回目标 R/P 的结构。几何接近参考 TS、能量峰或一个虚频只是中间证据。

```text
已映射 R/P + 端点几何
        │
        ▼
G0 数据与划分 → G1 反应编辑、选边与冻结 ScanPlan
        │                           │
        └─────────── PES generation：G2 执行扫描/路径、质检 ── PathBundle
                                                                │
                  PES ranking：路径可用性/拒绝 → 帧排序 → SeedProposal
                                                                │
                        PES2TS 端到端接口 ──→ RPH/ACP 执行 OptTS、频率、IRC
                                                       │
                                      ValidationResult 回流到隔离的评估区
```

ACP 提供任务执行、资源预算、日志、失败恢复和溯源；RPH 可消费初猜并承担既有 QC 验证链。PES2TS 不把执行基础设施、数据真值或下游 QC 引擎内化为排序模型。将来即使换成独立 QC 执行器，`SeedProposal` 与 `ValidationResult` 的合同不变。

## 2. 现有基础与必须先修的边界

| 已有资产 | 可直接利用的部分 | Demo 前的动作 |
| --- | --- | --- |
| G0/Reaction-QM | 冻结 split、端点库存、真值隔离与拒绝账本 | 保持反应级 split，核查逆向及近重复跨集合情况 |
| G1 v2 | 互斥编辑、H 伙伴变化、芳香/键级变化、L0/L0u/L1 和已运行的 gate | 将[完整逐反应 `scan_plan_v1` 方案](../design/G1_v2_补全实施总方案.md)落地；当前 gate 通过**不代表**计划已生成 |
| 首轮候选 | [24 条候选表](../../data/manifests/pes2ts_demo24_candidates_v1.csv)：8 层，每层 2 train + 1 valid | 人工复核后冻结；目前是候选，不是已验证的基元反应或成功样本 |
| RPH 经验 | 成键锚点反向拉伸、同步距离约束和 TS 后续优化经验 | 转为 G1 的候选生成启发式，并在 PES generation 内测量有效率 |

**第一项阻断修复：** 当前 G1 v2 导出带有 P1/IRC 派生的 `status_summary.endpoint_match`、`orientation`。G2 和 ranking 只接受端点与计划的正向白名单字段，导出器及验证器必须同时改；对已有导出不能仅靠删除列而跳过重新验证。当前 P1 映射来源标记为 `truth_assisted_p1`，首轮可用于工程调试，但正式泛化结论必须注明这一条件，或建立端点独立的映射对照。`scan_ready`、`multiplicity_max=1` 也不能分别解释为“可得到路径”和“所有端点局部闭壳层”。

## 3. 两个项目各自交付什么

### A. PES generation：反应到可审计的路径

**输入：** 端点 R/P、映射原子序、G1 编辑记录、预算与方法配置。**G1 决策：** 给每条反应冻结有限 `ScanPlan` 候选树，明确选哪一侧作成键锚点、实际拉伸方向、驱动键/观察键、扫描范围、约束和优化自由度、端点装配、多候选顺序及失败回退。G1 不运行 QC，也不依据 TS/IRC 真值选计划。**G2 执行：** 调用 ACP 中的 xTB/ORCA 等计算作业，产出逐帧结构与能量，按化学和数值规则质检。路径不合法时保留失败记录。

第一层用**一维进度变量** `s`：单键形成/断裂或 H 转移用一根主驱动距离；两到三根键的协同变化可以用同一个 `s` 驱动多根距离的分段目标，同时优化其余自由度，并将另一侧断键、键级、角/二面角作为观察或必要时的辅助约束。这是沿受限路径采样，**不等同**于独立二维/三维网格。双向选边按 G1 的几何与化学可构造性决定，不强制所有反应都套一维扫描。H₂、芳香/键级主导、高编辑数和多组分装配先有专门处理；扫描不能给出连续、合理路径时走双端 PATH/NEB 或明确拒绝。xTB 可作廉价预筛，关键比较保持同一能量定义和几何来源。

**交付：** 每个计划候选一个 `PathBundle` 或带原因的失败记录。`PathBundle` 至少含反应与 split ID、计划/方法/方向、统一原子序、端点来源、逐帧坐标和可比能量、驱动及观察键进度、优化收敛与碰撞/拓扑标记、计算资源与日志路径、版本和哈希。即使起点、终点能量高于内部峰，也必须保留完整帧与端点质量信息。

**自身问题：** 从全部计划反应到输入可构造、计算完成、化学有效路径分别有多少？每层失败是什么？每条有效路径耗费多少核时？不借排序成绩来掩盖路径缺失。

### B. PES ranking：路径到可提交的初猜

**输入：** 任意来源、符合相同合同的 `PathBundle` 集合；不读取隐藏 TS/IRC 坐标、真值标签或生成器私有状态。先做路径可用性判定和**可拒绝**决策，再在有效路径内部排序真实帧；当同一反应有多条有效路径时，最后比较路径间候选。输出 Top-k 帧及理由、置信或拒绝原因，保留反应原方向身份。初版先做确定性规则：内部能量峰、全局最高点、成断键进度、几何连续性、局部曲率和路径质量。高能端点不自动等于过渡区域。

**学习模型不是 Demo 前提。** 先量化“最佳可选帧”与强基线的差距：几何 oracle 只能作为诊断上界，真正有用的 oracle 需在小样本上通过同条件 OptTS/频率/IRC 及成本验证。如果路径中没有可用初猜，反馈给 generation；有明显选点空间且在较大训练集上稳定时，才训练轻量排序器。模型只能使用部署时能获得的特征。

**交付：** `SeedProposal`，至少含 reaction/path/frame ID、原子序和 XYZ、候选顺序、排序方法与版本、路径质量证据、拒绝原因、成本预估与溯源。排序器可在冻结的路径集合上独立迭代，不要求每次更换扫描方法都重训。

**自身问题：** 在**同一批有效路径**、同一 Top-k 与 QC 预算下，它是否比最强简单规则更常给出正确 TS 初猜，或降低每个正确 TS 的总核时？

## 4. 共同合同与数据隔离

| 合同 | 生产者 → 消费者 | 最小不变量 |
| --- | --- | --- |
| `ReactionCase` | G0/G1 → generation | 反应 ID、split、端点原子映射与几何、总电荷/多重度、G1 编辑、来源；真值字段禁止 |
| `ScanPlan v1` | G1 → G2 | 有限候选与预排序、原始和算法方向、驱动/观察坐标、初始几何、参数/预算/回退、静态可构造性、哈希 |
| `PathBundle v1` | generation → ranking | 同一原子序与能量口径；逐帧坐标/能量/状态；路径方法及成本；异常可辨认，绝不伪装成功 |
| `SeedProposal v1` | ranking → 验证器/RPH | 真正存在的帧 ID、XYZ、排名、依据、拒绝原因；候选与源路径可互相追溯 |
| `ValidationResult v1` | 验证器 → 隔离评估区 | OptTS/频率/IRC 各阶段状态、目标端点匹配、耗时/核时、失败与重试；不得回流生成或推理输入 |

首轮实现时，为每种合同提供 JSON Schema（或等价可执行 schema）、纯端点正向字段白名单、版本号与样本示例。G1 的 P1/IRC 注释单独保留在评估侧。所有选择、阈值、路径参数和比较方法在读取 valid/test 结果前冻结；首轮 16 train 可用于调试，8 valid 用于锁定后的检查，**没有首轮 test 结论**。

### 建议的代码与发布边界

首版沿用当前仓库，按接口隔离项目，合同稳定后可以独立发布 generation 与 ranking。现有 `pes2ts_core/g0/` 和 `pes2ts_core/g1/` 保留；新增模块建议为：

```text
pes2ts_core/contracts/       # 五种合同的 schema、读写与版本兼容检查
pes2ts_core/g2/              # PES generation：计划执行、帧收集、路径质检
pes2ts_core/ranking/         # PES ranking：拒绝、规则基线、Top-k；只依赖 contracts
pes2ts_core/evaluation/      # 隔离真值、OptTS/Freq/IRC 结果、分母与成本统计
pes2ts_core/integration/     # ACP 作业适配、RPH 候选适配与端到端清单
```

最小命令合同是 `plan → generate → rank → validate → report`，每一步读取前一步的版本化清单、写出新清单及失败账本，允许按 reaction ID 重跑而不覆盖旧结果。`ranking` 的接口测试应使用一份手工构造的合规 `PathBundle`，证明它不依赖 G2 的内部文件；G2 的测试则只检查计划可执行性和路径合同，不读取参考 TS。先形成一条可回放的纵向切片，再扩成 24 条分层 Demo。

## 5. 24 条 Demo 的明确实验

当前名单覆盖 A H 转移、B 单键、C 取代、D 双键协同、E 三键协同、F H₂、G 芳香/键级、H 高编辑数回退，共 **16 train + 8 valid**。A–E 的 15 条是扫描/同步进度的核心检验；F–H 的 9 条专门暴露特殊事件与回退。人工复核反应是否像单个基元步骤、电子态、映射、端点坐标与多组分装配；不合格者在任何 PES/TS 结果出现前，按[既定同层替补规则](../demo/PES2TS_demo24_反应挑选与复核方案.md)替换，并记录原因。

1. **Generation 主运行：** 冻结每条的 G1 首选和至多两个有限回退候选；对接受的 24 条逐条执行，保留每次尝试。核心 15 条应分别有至少一个可分析的有效路径，若某层完全失败，先修 G1/G2 再谈该层排序。F–H 可合理拒绝，但原因和成本要闭合。
2. **方法对照：** 在运行前，从 train 中按简单/协同/复杂机制预选约 6 条，对同一反应做“受限扫描 vs 双端 PATH/NEB”配对。这个对照回答路径方法的覆盖、质量和成本；它不被混作排序器提升。
3. **Ranking 主运行：** 对同一 `PathBundle` 跑全局最高能帧、内部峰、键进度/连续性规则与可拒绝策略。每种方法固定 Top-1；Top-3 另列。只在合格路径分母上比较排序，另报告从全部 24 条出发的端到端覆盖率。
4. **物理验证：** 对锁定的 valid 8 条，在可用路径上配对送交“最强预先指定简单基线”和“当前排序规则”的 Top-1 帧，使用相同 OptTS、频率、IRC、超时和重试预算；同帧只算一次。不可计算和拒绝也计入 8 条的端到端分母。train 样本可供诊断，但不用于宣称泛化效果。
5. **Demo 出口：** 展示每条反应的原始 R/P、G1 计划、路径动画/能量剖面、驱动/观察键进度、候选帧、两条 QC 结论及失败账本。24 条刻意分层且数量很小，只能证明链路和暴露问题，不能估计全库总体成功率或模型泛化。

统一漏斗是：`候选 24 → 人工接受 → 输入可构造 → 路径完成 → 路径化学有效 → 有候选/拒绝 → OptTS → 频率 → 双向 IRC 目标匹配`。每一步报告数量、分层、总核时和失败原因；禁止只对最终成功案例计算平均成本。

## 6. 分层开发顺序与转段条件

| 层 | 开发任务与可交付结果 | 继续推进的证据 |
| --- | --- | --- |
| 0 · 封口 | 修 G1 导出真值泄漏；完成 24 条双人化学复核及锁定清单 | 输入 schema/白名单通过；每条接受/拒绝有原因；valid 未被结果驱动替换 |
| 1 · 共同接口 | `ReactionCase`、`ScanPlan`、`PathBundle`、`SeedProposal`、`ValidationResult` 的 schema、示例、哈希与 ACP 执行适配 | 用假路径可走通生成→排序→验证记录，原子序与方向往返不丢失 |
| 2 · generation 最小路径 | G1 单键/H 转移计划，G2 一维受限优化、能量/几何质检、失败落盘；先做 A/B，再 C | A/B/C 各有可复核的有效实例；每次失败可定位计划、输入或 QC 阶段 |
| 3 · generation 扩展 | D/E 共用进度的多键约束，F/G 专门规则，H 与不适用反应的 PATH/NEB 回退 | 核心 A–E 每层有路径或明确可复现的阻断；完整 24 漏斗闭合；成本按方法拆开 |
| 4 · ranking 基线 | 路径有效性/拒绝、同路径 Top-1/Top-3 规则、几何与 QC oracle gap | 对有效路径同帧预算复算一致；明确是路径缺失还是选点错误 |
| 5 · 集成 Demo | 以 valid 8 的锁定对照运行 OptTS/频率/IRC，生成案例页与失败报告 | 能指出每条反应的停止位置和成本；完整流程可由清单复跑；不以 8 条做显著性结论 |
| 6 · 分层试点 | 另抽 200–1000 条，反应级去重/近重复审计，固定验证/测试策略，估计覆盖与 oracle gap | 各机制类路径有效率、排序增益、成功成本及不确定区间清楚；再决定是否训练模型 |
| 7 · 学习与扩展 | 仅在有稳定排序空间时训练轻量模型；再视需要扩到万级有效路径 | 冻结测试集和同预算物理验证优于最强适用规则，才扩大计算与对接范围 |

本轮**最短可运行切片**是：选一条已复核 A/B 反应 → G1 冻结单驱动计划 → G2 跑一条廉价路径 → 排序器给出最高能与内部峰 Top-1 → 相同协议送 OptTS/频率/IRC → 完整账本与可视化。它验证接口和成本记账，不能代替 24 条分层 Demo。

## 7. 评价口径与决策

**Generation 指标：** `输入可构造数 / 计划数`、`完成数 / 可构造数`、`化学有效数 / 完成数`，以及 `化学有效数 / 全部计划数`；按 A–H、方法、方向和多组分情况展开。报告每条尝试的核时和拒绝原因。

**Ranking 指标：** 仅在完全相同、冻结的有效路径集合上比较 Top-1/Top-3 目标 TS 成功、OptTS 核时与拒绝率；同时给出最高能帧、内部峰、键进度规则。几何 oracle 和参考 TS 距离只作为诊断，不能代替严格 QC 结果。跨路径选择另列，避免与同路径帧排序混淆。

**PES2TS 集成指标：** `正确 TS＋双向 IRC 的反应数 / 全部测试反应数`；`所有尝试的 QC 核时 / 正确完成反应数`，并报告从输入到首个正确 TS 的壁钟时间。失败、回退与超时照记。到独立试点阶段再用反应级配对区间做结论；24 条 Demo 只给逐例证据和描述统计。

当有效路径不足时，优先改 G1/G2 计划与端点；当路径已有可用帧而规则选错时，改 ranking；当候选合理却 OptTS/IRC 不过时，检查验证协议、路径能量级别和候选几何质量。这个错误归因决定资源投向，避免把所有失败都归到“模型不够大”。

## 8. 团队同步时统一替换的说法

| 旧表达 | 新表达 |
| --- | --- |
| “PES2TS 是一个路径帧排序模型” | “PES2TS 是 PES generation 与 PES ranking 的集成；排序器是其中一个可替换组件” |
| “生成 PES 曲线/完整势能面” | “在受限优化或双端方法下采样近似反应路径的能量剖面” |
| “G2 默认双端 xTB PATH” | “G1 冻结有限扫描/路径候选；G2 优先执行适用的一维进度扫描，不适用或失败时按计划回退 PATH/NEB” |
| “所有反应都能一维扫描” | “所有反应都应得到可审计的计划状态；适用的一维/同步扫描、双端方法和明确拒绝分别计数” |
| “闭壳层中性反应集” | “当前队列的总电荷为 0、记录的多重度为 1；逐条复核局域自由基和形式电荷” |
| “高能峰/TS 几何近就是成功” | “候选须以同预算 OptTS、频率和双向 IRC 目标端点验证实际价值” |
| “G3 标签属于路径生成” | “标签与评估是隔离的共享服务；generation 的推理输出不含真值” |

后续接口和实现说明均以本文的边界为准。旧资料中的反应类别、扫描化学、基线和 QC 原则可沿用；旧规模顺序和 PATH 默认策略不再作为执行依据。
