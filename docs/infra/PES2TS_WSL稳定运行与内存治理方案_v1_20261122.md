## 0. 摘要

2026-11-22 凌晨与上午，DSH 桌面端连续两次以同一原因退出：**GUI 渲染进程被 OOM 杀死**（`Desktop renderer exited: oom`），导致正在执行的智能体轮次中止。硬证据表明这不是模型或智能体逻辑问题，而是**宿主 Windows 提交内存（commit）被吃干**：WSL2 的 `vmmemWSL` 在 30 天内 6 次冲到 21–30 GB，其中两次与崩溃同一秒/十秒内触发 Windows 低虚拟内存事件（Event 2004）。

本方案把治理拆成**四层防线**，并给出**可执行脚本 + 阈值 + SOP**：

| 防线 | 内容 | 目标 |
|---|---|---|
| **F1 配置层** | `.wslconfig` 保持 36 GB reviewed floor / swap=0 / gradual；数据审计日可选 `dropcache` 严格档 | WSL 不被错误配置放大 |
| **F2 宿主编排层** | 页面文件迁 D: 固定 24–32 GB；C: 清盘；preflight 巡检；危险时 `wsl --shutdown` | commit 限额 ≥ 90 GB，留足安全余量 |
| **F3 Guest 执行层** | 每次重活走 `wsl_guarded_run.sh`（cgroup `MemoryMax`）；禁止全量读大文件；阶段末 `wsl_reclaim.sh` | 单任务无法把 vmmem 顶穿宿主 |
| **F4 会话/编排层** | 重活后台跑 + 日志落盘；工具输出限幅；按阶段 `wsl --shutdown`；DSH 会话拆分 | 减少 renderer/宿主内存叠加 |

**验收目标**：连续 7 天运行 V5.5/V5.6 作业期间，`vmmemWSL < 20 GB`、`commit 余量 > 15 GB`、无新增 Event 2004、无 DSH/进程 OOM 崩溃。

## 2. 根因模型（四层因果链）

```text
L0 触发：全量读大文件（wc 19.9GB csv / np.load 9.9GB npz / 24GB csv）
   ↓
L1 放大：WSL guest 页缓存 + 匿名内存上涨；memory=36GB 上限、swap=0 不能换出、
        autoMemoryReclaim=gradual 回收慢 → vmmemWSL 21–30GB 持续占用宿主 commit
   ↓
L2 宿主：pagefile 仅 9.6GB 且位于仅剩 22.4GB 的 C: 盘 → commit 限额 72.6GB；
        Chrome×2（2.4–2.7GB×2）、Office/ChatGPT/Edge 等常驻 → commit 逼近上限
   ↓
L3 受害者：Windows 低虚拟内存（Event 2004）→ Chromium 渲染进程申请内存失败
        → render-process-gone: oom → DSH 主进程抛错退出 → 轮次中止
```

**结论**：WSL 本身"没崩"，但**WSL 的内存膨胀触发了宿主级资源耗尽**，DSH 的 GUI 渲染进程是第一个被牺牲的。治理必须同时覆盖 WSL（F1/F3）、宿主（F2）与使用方式（F4）。

> 历史呼应：`config/wslconfig.recommended.ini` 记录的 2026-10-22 事故（memory=56GB 导致宿主 OOM，Hyper-V `StorageVSP 0xC000012D STATUS_COMMITMENT_LIMIT` → vCPU triple fault）与本次属同一类失败模式。**只调 WSL 上限不足以防止宿主被吃穿，必须同时约束"单任务实际用量"与"宿主 commit 余量"。**

## 4. 四层防线

### F1 · 配置层（`.wslconfig`）

维持 `config/wslconfig.recommended.ini` 的 reviewed 值：

```ini
[wsl2]
memory=36GB
swap=0
[experimental]
autoMemoryReclaim=gradual
```

- **swap=0 是硬策略**，不得开启（SSD 磨损 + 换页后延迟崩塌，换页完成的运行视为失败运行）。
- 数据审计日可选**严格档**：`autoMemoryReclaim=dropcache`（更积极归还页缓存；代价是重读盘变慢）。改后必须 `wsl --shutdown` 才生效。
- 禁止擅自调大 `memory`（56 GB 曾直接导致 2026-10-22 宿主 OOM）。

### F2 · 宿主编排层（Windows）

1. **页面文件迁到 D: 并固定 24–32 GB**（需管理员 + 重启）：
   系统属性 → 高级 → 性能设置 → 高级 → 虚拟内存 → 更改：
   - C: 设为"无分页文件"（或 2–4 GB 系统崩溃转储用）；
   - D: 设为"自定义大小"，初始 24576 MB，最大 32768 MB；
   - 重启。
   预期 commit 限额从 ≈72.6 GB 提到 **≈95–103 GB**。
2. **C: 清盘到 ≥30 GB**（页面文件、临时文件、缓存）。
3. **巡检**：计划任务每 5 分钟运行
   `powershell -ExecutionPolicy Bypass -File <repo>\scripts\infra\wsl_stability_check.ps1 -Json`，输出写入 `outputs/ops/wsl_stability/`（保留 7 天）。
4. **熔断**：巡检为 CRIT 且 WSL Running 时，可加 `-AutoShutdown` 自动 `wsl --shutdown`（默认关闭，先观察一周再加）。
5. **VHDX 体积**：`E:\WSL\ext4.vhdx` 当前 358.2 GB；每月检查 E: 余量，必要时 `wsl --manage Ubuntu --set-sparse true` + 停机压缩（Windows 11 `Optimize-VHD` 或 `diskpart compact vdisk`）。压缩前必须 `wsl --shutdown`。

### F3 · Guest 执行层（WSL 内）

**硬性数据访问规则（违反即视为重活不安全）**：

| 禁止 | 替代 |
|---|---|
| `np.load(multi-GB.npz)` 后遍历全部数组 | 只按需读取单个数组；`.npy` 用 `mmap_mode='r'` |
| `wc -l` 扫 10+ GB CSV | 使用 `data_manifest.json`/`curves.json` 已登记的行数；必须扫时用 `awk` 分段或 `wc` 前后 `drop_caches` |
| 一次 `pd.read_csv(24GB)` | `chunksize` 分块 + 只取所需列 + 先落 parquet |
| 在 `/mnt/e`（9p）上跑重 IO | 数据用 `/pes2ts_data`（ext4），临时文件写 `/tmp` 或 `/root/scratch` |
| 长驻 WSL 连续数小时不释放 | 每个阶段结束 `wsl --shutdown`（vmmem 立即归零） |

**每次重活必须通过受限运行器**（默认委托既有 `cgroup_scope.sh`，产物即"内存证据"）：

```bash
# Windows → WSL
wsl -e bash /mnt/e/Calculations/AI4S_ML_Studys/PES2TS/scripts/infra/wsl_guarded_run.sh \
  --mem 12G --name v55-audit -- \
  /root/miniforge3/envs/pes2ts-gpu/bin/python scripts/v55/audit_data_assets.py
```

- 超过 `MemoryMax` 时 cgroup 直接杀掉**该任务**（exit=137），不会拖垮宿主；看到 137 说明分片太大，缩小后重跑。
- 每次运行会在 `outputs/ops/wsl_stability/cgroup/<name>-<ts>/` 留下 `cgroup_sample.csv`（2s 采样）、`cgroup_summary.json`（peak_anon/oom_kill/gate）——这是"该任务峰值内存"的可审计证据。
- 训练任务建议 `--mem 16G`（不加 `--cpu` 以保留采样；如需 CPU 配额可显式指定，但会失去 cgroup 采样 CSV），并配合 `batch`/`num_workers` 上限。

**阶段末回收**：

```bash
wsl -e bash /mnt/e/.../scripts/infra/wsl_reclaim.sh
# 然后 Windows 侧：
wsl --shutdown
```

### F4 · 会话/编排层（DSH 与智能体团队）

1. **重活后台跑**：用后台 job + 日志文件（`outputs/.../logs/*.log`），工具只回读摘要；禁止在会话里打印大数组/大 JSON（本次事故前有 154 KB 与 100 KB 级输出，会放大 renderer 内存）。
2. **工具输出限幅**：大结果写文件后 `read` 摘录（`limit`/`offset`），单次输出建议 < 10 KB。
3. **会话拆分**：单会话超过 ~150 步或跨阶段时，另开新会话并用 `.slim/deepwork/v55-v56/STATE.md` 交接；长 transcript 会持续增大 GUI 渲染端内存。
4. **时间段错峰**：跑数据审计/训练时关闭不需要的 Chrome/Edge/Office/ChatGPT/Antigravity 等重型进程。
5. **preflight 前置**：每个重活批次启动前先跑 `wsl_stability_check.ps1 -Heavy`；非 0 不启动。

## 5. 标准作业流程（SOP）

### 5.1 开工前（Preflight，1 分钟）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\infra\wsl_stability_check.ps1 -Heavy
```

- exit=0（OK）→ 继续；
- exit=1（WARN）→ 只做收尾/读取类工作；先 `wsl_reclaim.sh`；
- exit=2（CRIT）→ 停止；`wsl --shutdown`；检查页面文件/C 盘；复检到 OK。

### 5.2 运行中（Guard）

- 所有重活经 `wsl_guarded_run.sh`（F3）；
- 每完成一个分片，检查：`wsl -e bash -c 'free -m | head -2'` 与宿主 `wsl_stability_check.ps1`；
- 出现 Event 2004 或 vmmem ≥ 20 GB：**立即停新任务**，收尾落盘 → `wsl_reclaim.sh` → `wsl --shutdown`。

### 5.3 收工（Wrap-up）

1. 产物落盘 + 记录 SHA/行数（审计脚本负责）；
2. `wsl_reclaim.sh`；
3. `wsl --shutdown`（**必须**，否则页缓存长期占宿主内存）；
4. 巡检复检一次，结果归档到 `outputs/ops/wsl_stability/`。

### 5.4 崩溃/挂死恢复（按场景）

| 场景 | 判别 | 处置 |
|---|---|---|
| DSH renderer OOM / 界面消失 | 崩溃日志含 `Desktop renderer exited: oom` | 不要连续重启重试；先 `wsl --shutdown` + `wsl_stability_check.ps1 -Heavy`，确认 OK 后再重开 DSH；从 `STATE.md` 恢复上下文 |
| vmmem 长时间不降 | `Get-Process vmmemWSL` 工作集不回落、commit 余量持续走低 | `wsl_reclaim.sh`；仍不降则 `wsl --shutdown`（重活已落盘时安全） |
| WSL 命令无响应 | `wsl -l -v` 卡住或超时 | `wsl --shutdown`；必要时 `Get-Service LxssManager` 重启（管理员）；再启动并检查 `dmesg` |
| WSL 启动失败 / VHDX 疑似损坏 | 事件日志 Hyper-V/StorageVSP 报错（如 `0xC000012D STATUS_COMMITMENT_LIMIT`） | 先释放宿主内存与 E: 空间，再 `wsl --shutdown` 重试；若 VHDX 损坏 → 使用 `wsl --export` 备份恢复（见 §7.3） |
| 训练任务被 cgroup 杀掉 | exit=137 | 缩小 `--mem` 对应分片/批大小；从最近 checkpoint 续跑 |

## 7. 训练任务（V5.6-A）专项约定

1. **顺序执行**：14 架构 × 1 seed 串行，不并行多个训练进程（GPU 仅 ~3.5 GB 空闲）。
2. **内存**：`wsl_guarded_run.sh --mem 16G`；DataLoader `num_workers` 默认 2–4，按 `free -m` 调整；优先 memmap（`samples/*.npy`）而非把全量样本读入内存；线程按 `scripts/infra/thread_caps.sh` 收敛（OMP/MKL/OpenBLAS/NumExpr=1），避免 numpy/BLAS 线程放大峰值。
3. **显存**：小批量（batch 32–128）+ 梯度累积；单 run 记录参数量与峰值显存（`torch.cuda.max_memory_allocated`）。
4. **checkpoint**：每个 epoch 存 `checkpoint_last.pt` + `checkpoint_best.pt`；如被 cgroup/宿主事件打断，从 `last` 续跑（复用 V5.4.3 supervisor 的思路：`outputs/pesn/v543_dual_decoder_50k/t4_supervisor.sh`）。
5. **日志**：每个 run 独立目录，stdout/stderr 落 `outputs/pesn/v56_screening/<arch>/train.log`；会话里只回读 `tail -n 50` + 指标 JSON。
6. **批次间释放**：每完成 3–4 个架构 `wsl_reclaim.sh`；每完成一个实验阶段 `wsl --shutdown`，并记录一次 `wsl_stability_check.ps1 -Heavy` 结果。
7. **安全边界**：训练数据只读（`/pes2ts_data`），产物只写 `outputs/`；中断重跑不删除既有 run 目录。

## 附录 B · 阈值依据

- commit 余量 15/20 GB：本次事故时余量 < 8 GB 即触发 Event 2004；DSH renderer OOM 前一刻几乎为零。留 15–20 GB 可覆盖浏览器/Office 的瞬时峰值。
- vmmem 20/14 GB：事故时 21–30 GB；36 GB 上限的 55%（20 GB）是"还能从容回收"的经验上限；重活模式 14 GB 给宿主留更多余量。
- Event 2004：Windows 已经诊断出低虚拟内存，等于"事故已发生，只是还没选好受害者"，因此重活模式下出现一次即 CRIT。
- C: 20 GB：小于此值时系统托管页面文件扩张失败概率显著上升（本次 22.4 GB 已接近边界）。
- E: 60 GB：`ext4.vhdx` 358 GB 已较大，余量过低时 WSL 扩容/写盘会失败。
