# MAINTENANCE — PES2TS 核心文档维护与讨论入档机制

> 任务：task-8；生成日期：2026-11-21；只读仓库（设计交付，未改既有文件）。
> 上位方案：`docs/infra/PES2TS_开发档案树与文档清理方案_v1_20261121.md` §4（维护机制）与 §5.6（Phase 5 启动）。
> 兼容基线（**不发明第二套机制**）：沿用 `> 状态：` 元数据头与 11 状态封闭词表（v2 方案 §5/§6）、台账增量登记、`docs/README.md` 索引、G5 门禁（`doc_manifest --check`）；本机制只规定"何时、由谁、按什么顺序"使用这些既有设施。
> 规模前提：**1 名所有者 + 若干 AI agent 会话**。所有流程都按"单会话 30–60 分钟可完成一次"设计；角色可兼任，但每份核心文档必须有且仅有一个 owner 角色。

## 0. 一页纸速览

| 节奏 | 何时 | 时长 | 一句话动作 | 产出 |
|---|---|---|---|---|
| **双周同步** | 隔周五（含异步版） | 30 min | 过"待落档队列"→判定树→更新文档/台账/索引 | 台账增量 ≥1 条；受影响文档与索引更新；`docs/agent_runs/FAQ.md`（如需） |
| **里程碑冻结评审** | 战役收口 / 阶段转换 / 发布前 | 60 min | 文档冻结：状态/版本/结论/负结果/报告链接核对 | 状态转换（台账+元数据头）+ 档案条目定稿 |
| **季度档案树刷新** | 每季末最后一周 | 120 min | 档案树刷新 + 度量化审计（复用 `doc_audit/` 模板） | 季度审计报告 + 指标对照 + 索引修正 |
| **事件驱动落档** | 讨论/决策结束 → **48h 内** | ≤15 min | 五类落点判定树（§3）→ 落档 → 登记 | 五类落点之一 + 台账一行（+ 档案树/README/FAQ 视落点） |

**三条铁律**：
1. **只登记在聊天/会话/issue 里不算落档**——48h 内没有写进仓库 = 没发生（讨论记录本身也按 §3.0 入档）。
2. **不新增索引**：所有落点最终都收敛到「元数据头 + 台账 + `docs/README.md` + G5 清单」三件套（v2 方案 §10.1）。
3. **先改规则再动文档**：涉及退役（删除）的只能在 Phase 0 治理修订（ADR-0035 + `AGENT.md` §9.4 例外）签认后执行。

## 1. 角色与 owner 制

### 1.1 四个 owner 角色（角色而非人名；可兼任）

| 角色 | 代号 | 职责 | 典型占用的受管单元 |
|---|---|---|---|
| **仓库所有者** | `OWNER` | 最终批准（A）；规范根/红线/退役/发布；唯一可签认 ADR、合同换代与退役的人 | 治理根、根 README、档案树规则 |
| **科学负责人** | `SCI` | 科学与任务语义：合同、阶段计划、ADR、评估口径、负结果表述 | 合同 C1–C3/C7、计划 P1–P5/P7、ADR 集、模型卡 |
| **工程负责人** | `ENG` | 代码/接口/运维：代码地图、模块划分、ACP 字段、脚本与数据产物说明 | 设计 D1/D3/D4、合同 C4–C6/C8、产品说明 E3–E7 |
| **Agent 会话** | `AGENT` | 执行代理：起草、机械登记、索引维护、档案抽取、门禁复跑；**不得作为规范性文档的最终 owner** | 台账、`docs/README`、G–V 投影、档案条目起草、FAQ、退役流水 |

> 1 人 + AI 会话的最小团队里，`OWNER/SCI/ENG` 可由同一人兼任——但**受管单元上只有一个名字**，避免"都管=没人管"；`AGENT` 可以拥有 G5/G6/G9/T2/T4/G10/G11 这类生成物/流水，规范类文件一律由人角色最终负责。

### 1.2 owner 职责（每个受管单元必做四件事）

1. **守状态头**：元数据头 8 字段（至少 状态/层级/取代关系/当前版本）在审查日核对一次；状态与事实不符时走 §5 矩阵。
2. **接落点**：本单元被判定树指到时，48h 内完成落档（可委派 `AGENT` 起草，所有者签认）。
3. **季度对账**：季度审计时对本单元回答一句"现状、变更、下季度预期"；过期无法回答 = 该单元失管，上报 `OWNER`。
4. **交接**：owner 变更/长会话结束前执行 §1.3 交接清单。

### 1.3 交接协议（换人 / 长会话结束 / 项目暂停）

**触发**：owner 角色换人；某战役收口且主导会话结束；连续 2 次双周会缺席。
**交接必须完成（30 分钟内，`AGENT` 可代办 4 项）**：
1. 受管单元清单签收：`DOC_OWNERS.csv` 中该角色名下逐行过一遍（状态/下次审查日/备注）。
2. 未落档队列移交：`docs/agent_runs/FAQ.md` 待决 + 台账最近 5 条 + 所有 `DISC-*` 未完结讨论。
3. 在途变更移交：未定稿的 ADR/合同版本、未完成的档案条目、未关的门禁红项。
4. 门禁基线：贴出最近一次 4 道文档门禁输出（`docs_consistency --strict` / `check_docs_links` / `render_gv_map --check` / registry tests；G5 落地后加 `doc_manifest --check`）。
5. 交接记录：在台账追加一条"owner 交接：<角色> <旧人>→<新人>，未决项 N 条"；在 `docs/agent_runs/handoffs/` 留一份会话交接（沿用既有 handoff 格式）。
6. `OWNER` 在 `DOC_OWNERS.csv` 改 owner 字段并更新下次审查日。

**会话级最小交接**（每次 AI 会话开始/结束）：开始读 `AGENT.md` §9 + `docs/README.md` + 台账最近 3 条；结束写 1 条台账增量（或"本次无文档变更"），不得只在对话里留结论。

## 3. 节奏二：讨论 → 文档的"五类落点"判定树

### 3.0 判定树（唯一入口；挂在 `docs/archive_tree/README.md` 与本文件）

```text
一次讨论/决策产生（含对话中的裁决）
│
├─ 0. 先判"是否只产生了一条可复用问答、且不改变任何现行依据？"
│     └─ 是 → ④ FAQ-QA（FAQ 条目，不是规范）
│
├─ 1. 是否改变架构/接口语义/红线/跨阶段边界，或需要记录被否掉的替代方案？
│     └─ 是 → ① ADR（新增 ADR-NNNN；Accepted 后生效）
│          └─ 若同时改变任务/数据/几何/接口契约 → 叠加 ② 合同变更（ADR 在前）
│
├─ 2. 是否改变数据/任务/几何/接口契约（字段、单位、语义、schema）？
│     └─ 是 → ② 合同变更（新版本 vN+1；旧版标 Superseded，不改正文）
│
├─ 3. 是否改变计划/排期/验收门/预算/范围/顺序？
│     └─ 是 → ③ 计划更新（元数据头 当前版本 bump + 变更记录 + 台账；
│              Frozen-Preregistered 不可原地改 → 新版本或 protocol_amendment）
│
├─ 4. 是否是某战役的结论/负结果/时间线补充，且不改变任何现行文档？
│     └─ 是 → ⑤ 档案树补充（对应期条目 §4/§5/§8 追加；定稿条目 Frozen 不改）
│
└─ 5. 以上皆否 → 不落档（在当期同步会记录"判定为不落档"及理由，防止重复讨论）
```

**判定顺序纪律**：①→②→③→④→⑤ **不是并列而是优先级**；一条讨论可能有**主落点 + 附带登记**（例：合同变更 = ②主 + ①ADR前置 + 台账/README 登记），但**最多 1 个主落点**，避免"一份内容四处复制"。

### 3.1 五类落点的触发条件 / 模板 / 登记位置 / 时限

| # | 落点 | 触发条件（满足任一） | 模板 | 落点位置 | 必须登记 | 时限 |
|---|---|---|---|---|---|---|
| ① | **ADR** | 改变架构/接口语义/红线；在两个以上方案间做了取舍；决策会影响后续≥2 个战役；门禁/合同语义换代 | `docs/design/decisions/ADR-<NNNN>-<标题>.md`（决策/背景/选项/决定/后果/关联 ADR；编号唯一连续） | `docs/design/decisions/` | 台账（日期+标题+状态+路径）+ `docs/README` 一行 + 关联合同/计划头部"取代关系" | 讨论后 **48h 内**出提案（`Active-Proposed`）；生效（`Accepted`）在 `OWNER` 签认时，≤5 个工作日 |
| ② | **合同变更** | 字段/单位/输入输出边界/标签定义/schema 语义变化；合同条款不适用于执行事实 | 新版本文件 `PES2TS_<名称>Contract_vN+1.md`（头部 8 字段 + §变更记录 + 取代关系）；旧版**只加横幅不改正文** | `docs/contracts/` | 台账（含"被 X 取代"）+ `docs/README` 合同节 + G5 取代闭环 + 下游计划"上游依赖" | 48h 内出草案；生效需 `OWNER` 签认（≤5 个工作日）；生效当日同 PR 改索引 |
| ③ | **计划更新** | 排期/范围/预算/验收门/顺序变化；执行完成需转 `Executed-Frozen`；战役收口 | 原文件 §变更记录 + 元数据头 `当前版本` bump + `取代关系`（如需）；`Frozen-Preregistered` 阶段禁止原地改语义 → 新版本或 amendment | `docs/plans/`（或 `docs/design/` 设计文档同规则） | 台账 + `docs/README` 状态列 + 若涉及报告则加报告链接 | **48h 内**（状态转换类当次同步会内完成） |
| ④ | **FAQ-QA** | 可复用的操作口径/排错/环境知识；**不改变规范**；同一问题被问第 2 次 | FAQ 模板（`DISCUSSION_TEMPLATE.md` §2：问题/适用场景/答案/依据/失效条件/维护者/复审日） | `docs/agent_runs/FAQ.md`（L4 运营层，**非规范**；稳定后再升格为合同/设计） | 台账一行（"FAQ 新增 FAQ-编号"）；同步会记录 | 48h 内；问答超过 3 条同类 → 评估升格为 ①/② |
| ⑤ | **档案树补充** | 战役 `Executed-Frozen`；负结果/时间线/阶段结论需要长期可读；过程文档退役前抽取结论 | `docs/archive_tree/_TEMPLATE.md` 对应字段（§4 成果 / §5 负结果 / §7 证据指针 / §8 文档处置） | `docs/archive_tree/<期号>.md` | `_INDEX.md` 一行 + `CHANGELOG.md` + 台账 + （退役时）`RETIRE_LOG.md` | **48h 内**落条目；退役抽取不晚于删除同批 |

**48h 计时规则**：从讨论产生明确结论/裁决那一刻起算；48h 内至少要有"落点已定 + 首次提交"，允许草案状态（`Active-Proposed`）后补；超时未落档 → 下一期双周会第一项，记为**落档逾期 1 次**（计入 §7 落档率）。

**讨论记录本身**：每场有结论的讨论在 `docs/agent_runs/discussions/YYYYMMDD_<主题>.md` 留一份（模板见 `DISCUSSION_TEMPLATE.md` §1），编号 `DISC-YYYYMMDD-NN`；它是**落点载体而非落点**——讨论记录必须链接到五类落点之一。

## 4. 节奏三：里程碑冻结评审（文档冻结）

**触发**（任一）：战役从 `Frozen-Preregistered` 进入执行前；执行完成 → `Executed-Frozen`；阶段转换（G#/C/R/X）；版本发布/推远端前；`OWNER` 要求的任何时点。
**时长**：60 分钟。**主持**：该战役 owner；**参与**：`OWNER`（或书面签认）+ `AGENT` 记录。

**冻结评审 checklist（8 项，全绿才可冻结）**：
- [ ] 方案/清单/ADR 状态头齐全且相互一致（`状态/层级/取代关系/当前版本`）
- [ ] 执行完成有证据：终报链接、registry 状态（`g_v_map.yaml` → G9 重渲染）、台账条目
- [ ] 负结果如实保留（失败/负结果/未验证项在 §5 或报告中可检索）
- [ ] 冻结件（config/阈值/预算/预注册）与本阶段文档无矛盾（数值逐一对）
- [ ] 旧版本已标 `Superseded` 并写明取代者（不删、不改正文）
- [ ] 档案树对应期条目已更新或已排期（结论/负结果/证据指针）
- [ ] 4 道文档门禁全绿（+ G5 若已接入；改代码/测试时加全仓 pytest）
- [ ] 台账已登记本次冻结；`docs/README` 状态列已同步

**产出**：① 状态转换（元数据头 + 台账 + README）；② 档案条目更新；③ 冻结评审记录（`docs/agent_runs/sessions/YYYYMMDD_freeze_<战役>.md`，一页）。

## 5. 变更流程与审批矩阵（L1–L4，沿用上位方案口径）

### 5.1 修订分级审批矩阵

| 级别 | 定义/示例 | 批准人 | 必须同步 | 时限 | 门禁要求 |
|---|---|---|---|---|---|
| **L1 勘误** | 错别字、断链、状态列笔误、索引行漏项、格式/编号笔误；**不改变任何语义** | `AGENT` 自审 + 留痕 | 台账一行（可合并当日多条）；受影响索引行 | 当日 | `check_docs_links` + `docs_consistency --strict`（G5 落地后加 `doc_manifest --check`） |
| **L2 状态转换/横幅** | `Active-Proposed→Executed-Frozen`、`Superseded` 横幅、`Historical/Deprecated` 降级、`docs/README` 状态列修正；**只改状态不改正文** | `OWNER` 确认事件（书面/会话单行即可） | 元数据头 + 台账（含理由+证据链接）+ README 状态列 + G5 取代闭环 | 事件发生后 48h | 4 道全跑；不得动门禁钉死路径的位置 |
| **L3 语义修订** | 结论/指标/口径/合同条款/计划范围变化 | `SCI`（技术内容）+ `OWNER`（规范性）签认；涉及合同换代必须新版本 | 新版本或 §变更记录 + `取代关系` + 台账 + INDEX/README + 下游"上游依赖" | 48h 起草，≤5 工作日生效 | 4 道全跑 + 冻结件数值核对；改代码/测试加全仓 pytest |
| **L4 新建/退役/迁移** | 新文档、`git rm` 退役、目录迁移、索引重构 | `OWNER` 批准（退役须 Phase 0 治理修订生效 + 恢复演练完成） | 元数据头 + 台账（退役动作）+ `RETIRE_LOG.md` + 档案树条目 + tag/bundle 记录 + 门禁配置同 PR | 按批次 PR（每批 ≤80 文件） | tag/bundle 可恢复验证 + 4 道 + 配置同步 + G–V 重渲染 |

**一键对照**：L1 = 不改语义 → 直接改；L2 = 只改状态 → 有事件证据即可；L3 = 改内容 → 双签认 + 版本 bump；L4 = 改存在性 → 先规则后动作 + 可恢复。

### 5.2 与 G5 门禁（`doc_manifest --check`）的衔接

| G5 校验项 | 本机制的哪个动作保证它 | 未落地前的替代 |
|---|---|---|
| 1 状态可解析（前 40 行） | 新建/修订按 v2 方案 §6.1 写 8 字段头；L1–L4 矩阵每次改状态都改头 | 人工核对 `DOC_OWNERS.csv` 季度抽检 |

## 6. 节奏四：季度档案树刷新（每期/战役结束后的强制归档动作）

### 6.1 触发

- **每期强制**：战役转入 `Executed-Frozen`（或阶段关闭）后 **1 个双周周期内**必须完成该期档案条目与归档动作；未完成不得进入下一战役的 Phase 3 删除。
- **每季度强制**：季末最后一周做全树刷新 + 度量化审计（复用 `docs/infra/doc_audit/` 模板，产出 `docs/infra/doc_audit/<YYYYMMDD>/`）。

### 6.2 档案树更新流程 checklist（从报告到条目，7 步）

- [ ] **1. 抽取**：只从**终报/台账/registry** 抽结论（≤10 行/期）：目标、核心思路 3–5 条、关键决策、量化成果（带口径）、负结果（预期 vs 实际 vs 归因）。
- [ ] **2. 写条目**：按 `_TEMPLATE.md` 填 §1–§8；`§5 负结果` 必填（无负结果写"本期无/不适用"及理由）；§7 证据指针写"原文路径 + 删除前 commit/tag"。
- [ ] **3. 关联**：关联 ADR 编号（A1 集）、合同版本（§2）、计划版本（§3）逐一对上；被否决的替代方案写进 §3。
- [ ] **4. 更新索引**：`_INDEX.md` 加一行（期号/时间/主题/一句话结论）；`CHANGELOG.md` 追加变更。
- [ ] **5. 登记台账**：台账追加"档案条目新增/更新：期号 + 路径 + 结论摘要"一条；`docs/README` 档案树入口行同步。
- [ ] **6. 处置文档**：需退役的过程稿按 Phase 3 批次执行（先抽取→再 `git rm`→ `RETIRE_LOG.md` 登记→tag 可恢复）；**不得**把过时文档搬进 `docs/archive/`（快照禁当墓地）。
- [ ] **7. 复跑门禁**：`docs_consistency --strict`、`check_docs_links`（0 error）、`render_gv_map --check`、registry tests；G5 落地后加 `doc_manifest --check`；`_INDEX` 与 `docs/README` 双索引无缺。

**完成判据**：条目评审通过（`OWNER` 抽读 1 期）+ 台账已登记 + 索引双无缺 + 门禁全绿。**不满足任一条 → 该期标记"归档未完成"，下期双周会第一项。**

### 6.3 季度审计（与档案树刷新同批）

1. 复跑 `doc_inventory`/`doc_manifest` 生成当季全量清单（证据入 `docs/infra/doc_audit/<YYYYMMDD>/`）。
2. 对照 §7 四指标 + v2 方案 §13.3 度量表，出"上升/持平/恶化"三档结论。
3. 抽查 ADR 1/3、合同全量、核心集状态头全量；过期状态列问题清单。
4. 修正 `DOC_OWNERS.csv` 的审查日；更新档案树。
5. 产出一页季度报告（结论 ≤10 条 + 债清单 + 下季目标），台账登记。

## 8. 反模式（明令禁止，与 v2 方案 §12 对齐）

1. **无 owner 文档**：未进 `DOC_OWNERS.csv` 的文档不得长期留在活跃面（要么纳入、要么退役、要么划为只读证据）。
2. **讨论不落档**：只在会话/聊天留结论；"下次再说"超过 2 次 = 落档逾期，进入季度债清单。
3. **FAQ 当规范**：FAQ 是运营知识，不得被引用为执行依据；需要约束力时升格为 ①/②。
4. **档案树当墓地**：把 `docs/archive_tree/` 当"旧文档堆放处"（只收结论化叙述）；把 `docs/archive/` 当过时文档墓地（快照只读、只增）。
5. **双索引漂移**：只改 README 不改台账（或反之）；以 G5 清单为准修索引。
6. **状态通胀**：随手新增状态词（封闭 11 词，扩展须修订 v2 方案）。
7. **维护机制空转**：只有模板没有节奏/度量——本机制的硬约束是"双周台账增量 ≥1 条 + 季度 4 指标"，其余可裁。
