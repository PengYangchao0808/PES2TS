## 0. 结论速览

**目标一句话**：把 253 条文档压缩为 **一棵开发档案树（7 期 / 17 条目 / 1 横切层，共约 32 份）+ 一套 44 个受管单元的核心文档集**；其余**过程性文档先抽结论入档案树，再从工作树退役**（git 历史 + tag/bundle 可一键恢复），并建立"讨论定期入档"的长效维护机制。

**两部分结构**（对应你的两个要求）：

| 部分 | 目标 | 产物 | 落点 |
|---|---|---|---|
| **第一部分：开发档案树** | 记录不同时间的核心开发思路与研究成果，删除多余文档 | `ARCHIVE_TREE` + 14 个分期条目 + 映射表 + 删除清单 | `docs/archive_tree/`（新）+ 退役过程性文档 |
| **第二部分：核心功能文档保留与维护** | 核心文档固定维护，讨论定期进文档 | 核心集（30–50 份）+ owner 制 + 双周同步 + 五类落点判定树 | 沿用 `docs/` 既有结构 + G5 门禁 |

**三档清理强度（默认推荐 `standard`）**：

| 档 | 删除量 | 保留量 | 适用 |
|---|---|---|---|
| `safe` | **63** | **190** | 已被取代且无独有结论的重复文档（56 份 `DELETE` + 7 份合并） | 低：不碰钉死路径、不碰 reports 正文 |
| **`standard`（推荐）** | **116** | **137** | 再删过程性文档 53 份（52 份"先抽结论再删"+ 1 合并） | 中：需档案树条目承接；links 修正 |
| `aggressive` | **152** | **101** | 再删 36 份（21 份长尾过程文档 + 15 份门禁配置改动后退役） | 高：必须同 PR 改门禁配置并重渲染 G–V |

**四条安全底线**：

1. **先改规则，再删文档**：Phase 0 新增 ADR「文档生命周期与退役政策」并修订 `AGENT.md` §9.4；未修订前**不执行任何删除**。
2. **不可恢复的删除不做**：删除前 `git tag` + `git bundle` + `docs/` 目录 tar 备份（全库文档仅 4.7 MB，备份成本可忽略）；每条删除都能用 `git show <tag>:<path>` 恢复。
3. **删除 ≠ 丢失结论**：凡有独有结论/负结果/数据的文档，先抽入档案树对应条目（`ARCHIVE_EXTRACT_THEN_DELETE`），**档案条目承载结论，git 历史承载原文**。
4. **永不删除清单**：宪法、`AGENT.md`、阶段定义、完整开发流方案、台账、`docs/README`、现行合同（5 份 `Active-Normative`）、全部 ADR、`artifacts/**/model_card.md`、`docs/agent_runs/state/gates/**`、`docs/archive/**/manifest|verification|README`、`docs/archive_tree/**`。

**执行顺序**：`Phase 0 治理修订 → Phase 1 保护性快照 → Phase 2 档案树落成 → Phase 3 分三批删除(D1/D2/D3) → Phase 4 索引/门禁收敛 → Phase 5 维护机制启动`。预计总工作量 **2–3 个工作日**（AI 会话辅助），其中档案树撰写约占 60%。

## 1. 现状判断：为什么可以大幅压缩

### 1.1 规模与构成（2026-11-21 全量盘点）

| 维度 | 数据 |
|---|---|
| 文档总量 | **253 条**（`.md` 245 / `.html` 4 / `.txt` 3 / `LICENSE` 1），**4.74 MiB**，55,452 行 |
| 时间分布 | 2026-09：34 条；**2026-10：207 条**；2026-11：11 条；1 条无日期 |
| 按目录 | plans 58、archive 36、reports 36、ADR 34、design 16、contracts 13、agent_runs 14、superseded 5、demo 3、infra 6、根 15、其它 24 |
| 按分类 | 活跃计划 23、冻结计划 11、已取代 12、历史提案 10、证据报告 36、ADRs 34、设计 23、合同 13、运营记录 22、快照 36、治理 8 |
| 状态头 | 177/253 有状态块；137 种原始状态值（官方 5 种） |
| 索引 | `docs/README.md` 133 条 / 台账 100 条 / 双缺 40 条 |
| 重复与取代 | 21 个版本家族 / 53 成员；6 组状态自相矛盾 |
| 结论密度 | 36 份报告中大量是**过程记录**（批次实施记录、环境探测、单轮诊断），核心结论通常只在 1–2 份终报中 |

### 1.2 判断（基于审计事实，不是"看着旧"）

1. **约 40% 文档是"过程流水"**：V4/V5 各代的批次记录、环境探测、单轮诊断、handoff 交接、根目录战役 memo——它们记录了"怎么做的"，但**结论已被终报/台账/ADR 覆盖**。
2. **约 25% 是"被取代的重复"**：同一主题的多版本方案/设计（21 个家族），只有最新一版或终报有当前价值。
3. **真正不可替代的约 30–35%**：治理根（8）、ADR（34）、现行合同（5–13）、档案级终报（约 10）、模型卡（8）、门禁证据、数据/划分说明。
4. **压缩收益**：活跃面从 180 份压到 **≈102 份（含新建档案树 32 份；既有文档 70 份）**后，新人/未来的自己只需读 **1 份索引 + 7 期 17 条目档案 + 44 个核心受管单元**即可掌握项目全貌；这正是"档案树"要解决的问题，而不是靠保留全部文档。

### 1.3 为什么不能直接"删光"

- **52 条门禁钉死路径**被 `docs_consistency_config.json`（historical 17 / required_files 27 / root_scope 9）与 `config/registry/g_v_map.yaml`（43 处 docs 引用）强校验，直接删会让 CI 与 registry 测试永久红。
- `docs/reports/**` 受 `AGENT.md` §9.4"报告永不改内容"约束；`docs/archive/**` 受"版本快照禁当墓地"约束——**删除这些需要先改规则（Phase 0）**。
- 项目最有价值的资产恰是**负结果**（V4.2–V4.7 负结果、V5.4.2 `no_backbone_winner`、H2 sign guard 失败、V5.3-MP 规模收益饱和等）——它们必须进档案树，不能被"清理"掉。

**档案条目统一模板**（`_TEMPLATE.md`）：

```markdown
# <期号> <时间范围> · <阶段主题>
> 档案状态：Frozen（档案只追加，不改写已定稿条目）
> 关联 ADR：ADR-00xx, …
> 代码/模型/数据指针：commit `<sha>` / `artifacts/...` / `data/...` / 原文档路径

## 1. 本期目标（一句话）
## 2. 核心开发思路（3–5 条，写"为什么这样做"）
## 3. 关键技术决策（决策内容 + 依据 + 被放弃的替代方案）
## 4. 主要成果（量化指标；无量化则写"结论级成果"）
## 5. 关键负结果（**必须如实保留**：预期 vs 实际 vs 归因）
## 6. 对后续的影响（哪些被继承、哪些被推翻）
## 7. 证据指针（原文路径 + git blob/commit；原文退役后仍可恢复）
## 8. 本期文档处置（保留/抽取/退役清单）
```

**写作红线**：只写文档中能找到证据的内容；不美化负结果；指标必须带口径（数据集/seed/评估协议）；不写"当前"结论到历史期（历史期只写当时结论）。

### 3.2 从现有文档抽取的流程

1. **建骨架**：先用统一模板建 `docs/archive_tree/` 的 README/INDEX/CHANGELOG + 7 期目录 + 17 期空条目。
2. **填示范成稿**：7 份已写好的示范成稿（E01/E03/E07/E10/E12/E13/E16）可直接落盘，作为其余 10 条的样板。
3. **填其余条目**：按"方案 + 合同 + 终报 + 台账增量"整理 E02/E04/E05/E06/E08/E09/E11/E14/E15/E17；**结论以终报为准**，方案只用来写"当时的思路"。
4. **负结果专项**：逐条列出各战役失败/负结果（数据、指标、归因），与 `docs/agent_runs/state/gates/*.json`、报告交叉核对。
5. **证据指针**：每期记录原文路径清单 + 删除前 git commit（Phase 1 的 tag 名）。
6. **评审**：由所有者抽读 3 期（建议 03/09/14）确认口径，再批量定稿。

**工作量估算**：每期 30–60 分钟（AI 起草 + 人工校核），17 期约 1.5–2 个工作日；全局条目 + 索引约 0.5 天。

### 3.3 档案树与现有 `docs/archive/` 的区别（防混用）

| | `docs/archive/`（既有） | `docs/archive_tree/`（本方案新增） |
|---|---|---|
| 存什么 | 某次修订的**字节级快照** | 按时间分期的**结论化叙述**（人读） |
| 形式 | `*.snapshot.txt` + manifest/哈希 | 结构化 markdown 条目（模板统一） |
| 读者 | 审计/追溯 | 未来的自己、新人、外部评审 |
| 可变性 | 只读、永不改 | 只追加；定稿条目 Frozen |
| 与删除的关系 | 保留快照即保留原文 | 档案条目 + git tag 共同替代"保留全部原文" |

## 4. 第二部分：核心文档保留与维护机制

### 4.1 维护节奏（单所有者 + AI 会话的小团队可执行）

| 节奏 | 动作 | 时长 | 产出 |
|---|---|---|---|
| **双周**（固定日，如周五） | 文档同步会：上周讨论/决策 → 落点判定 → 更新对应文档 → 台账登记 | 30 分钟 | 台账增量 1 条 + 受影响文档更新 |
| **每里程碑**（战役收口/阶段转换） | 文档冻结评审：状态头/版本/结论/负结果核对；触发档案树条目更新 | 1 小时 | 状态转换 + 档案条目 |
| **每季度** | 档案树刷新 + 度量化审计（复用 `doc_audit/` 模板） | 2 小时 | 季度审计报告 + 索引修正 |
| **随时** | 临时讨论/决策：48 小时内落档（判定树见 §4.3） | ≤15 分钟 | 五类落点之一 |

**30 分钟双周议程模板**：① 回顾上次落档项（5 min）→ ② 本周讨论/决策过判定树（15 min）→ ③ 更新核心文档 + 台账（8 min）→ ④ 确认下次审查项（2 min）。

### 4.2 文档 owner 制（角色而非人名）

| 角色 | 代号 | 职责 | 典型受管单元 |
|---|---|---|---|
| 仓库所有者 | `OWNER` | 最终批准：规范根/红线/退役/发布；唯一可签认 ADR、合同换代与退役 | 治理根、根 README、档案树规则 |
| 科学负责人 | `SCI` | 科学与任务语义：合同、阶段计划、ADR、评估口径、负结果表述 | C1–C3/C7、P1–P5/P7、ADR 集、模型卡 |
| 工程负责人 | `ENG` | 代码/接口/运维：代码地图、模块划分、ACP 字段、脚本与数据说明 | D1/D3/D4、C4–C6/C8、产品说明 |
| Agent 会话 | `AGENT` | 执行代理：起草、登记、索引维护、档案抽取、门禁复跑；**不得作为规范文档最终 owner** | 台账、`docs/README`、G–V 投影、档案条目起草、FAQ、退役流水 |

> 1 人 + AI 会话的小团队里 `OWNER/SCI/ENG` 可由同一人兼任，但**每个受管单元只挂一个名字**（避免"都管=没人管"）；规范类文件一律由人角色最终负责。逐单元映射见 [DOC_OWNERS.csv](doc_cleanup/20261121/DOC_OWNERS.csv)。

**交接协议**：owner 变更/会话结束前，必须完成：① 受影响文档状态头"下游消费者/当前版本"更新；② 台账登记交接；③ 档案树"本期文档处置"更新；④ 未决问题写入台账待办。

### 4.3 讨论 → 文档的"五类落点"判定树

```text
讨论/结论产生
├─ 是否改变了架构/接口/红线？ ──是→ ① ADR（新增 ADR-NNNN；Accepted 后生效）
├─ 是否改变了数据/任务/几何/接口契约？ ──是→ ② 合同更新（新版本 vN+1；旧版标 Superseded）
├─ 是否改变了计划/排期/验收门？ ──是→ ③ 计划更新（状态头 + §变更记录 + 台账）
├─ 是否是复用型问答/操作口径？ ──是→ ④ FAQ/操作文档（核心集内新增一页或并入现有页）
└─ 是否是阶段性结论/负结果？ ──是→ ⑤ 档案树条目（当期条目 §4/§5 追加，或新期条目）
```

**时限**：讨论结束 **48 小时内**必须落档；只登记在聊天/issue 里不算落档。**判定树挂在 `docs/archive_tree/README.md` 与核心集索引，防止遗忘。**

### 4.4 修订分级审批矩阵

| 级别 | 例子 | 审批 | 门禁 |
|---|---|---|---|
| L1 勘误 | 错别字、断链、状态列笔误 | 直接改 | links + consistency |
| L2 状态转换 | Active→Executed、Superseded 横幅 | 所有者确认事件 | 台账登记 + 4 门 |
| L3 语义修订 | 结论/指标/合同条款变化 | 所有者签认（ADR/合同版本） | 新版本 + 全套门禁 |
| L4 新建/退役 | 新文档、删除/迁移 | 所有者批准（Phase 3 流程） | tag/bundle + 配置同步 + 4 门 |

## 7. 风险与回滚

| # | 风险 | 触发 | 后果 | 缓解 |
|---|---|---|---|---|
| 1 | 误删有独有结论的文档 | 判定只看"重复"没看"结论" | 不可逆信息损失 | 强制"先抽取→再删除"；`unique_value` 字段把关；Phase 1 tag/bundle |
| 2 | 断链/断门禁 | 删除被引用或钉死路径 | CI 红、registry 测试失败 | 前置 grep + 同 PR 改配置 + 4 门 |
| 3 | 档案树写成流水账 | 抽取时照抄报告 | 树失去价值 | 条目模板强制"思路/决策/成果/负结果/影响"五段；所有者抽审 3 期 |
| 4 | 负结果被"清理"掉 | 把失败报告当过程文档删 | 失去最有价值资产 | `unique_value=高` 一律 `ARCHIVE_EXTRACT_THEN_DELETE`，且条目 §5 必填 |
| 5 | 维护机制空转 | 没有节奏/owner | 3 个月后回到现状 | 双周固定日程 + 台账强制 + 季度度量 |
| 6 | 删除范围失控 | 一次性大批量 | 排查困难 | 三批独立 PR + 每批 ≤80 文件 + tag 打点 |

**回滚（任一阶段）**：`git reset --hard <tag>` / `git restore --source=pre-doc-purge-20261121 -- <path>` / `git bundle` 重建仓库副本（最坏情况）。
