## 2. 方法：为什么用曲线而不是 seed 做区间

`metrics.json` 只留聚合值（`evaluate_checkpoint` 丢弃了 per-cluster 字典），
所以本轮先按**训练时完全相同的代码路径**重评，把 per-curve 值取回来：

- Move/g53：只在 `label_status == "ok"` 的 116,527 个 dev 位置上评估（与 `evaluate_v53mp` 一致）；
- q / endpoint：在全部 135,926 个 dev 位置上评估（589 条 curve、113,040 行未 mask）。

统计单位取 **冻结 dev curve**（557 条有 Move 分母、534 条有可判 sign 的 pair、589 条有 q）。
两档的 curve 集合**完全相同**（`corpus.identical = true`），且 18 个 run 的
active pair 数都是 **6,142** —— 配对比较是在同一批 pair 上做的。

区间 = paired curve bootstrap（10,000 draws，固定 seed = run seed）。
`*` 表示 95% CI 不跨 0。

## 5. 怎么读这三条

1. **上一版报告里“20k→50k Move 增益落在噪声里”的说法要修正。**
   当时用的是 `metrics.json` 里的**非配对** cluster bootstrap，两个 CI 大幅重叠；
   配对之后（同一批 6,142 个 pair、同一批 557 条 curve）区间收窄到 ±0.002，
   −0.35% ~ −0.82% 的改善是真实存在的。**但效应量仍然只有千分之几，工程意义有限。**
2. **Move 的“变好”有代价，而且代价可测。**
   dead-zone 从 5.86%→6.56%（A）、4.79%→6.30%（B）、5.04%→6.00%（C）；
   把弃权从 sign 里扣掉后的条件方向准确率（`sign/(1−dead)`）也掉了约 1 个百分点
   （A 0.9120→0.9008、B 0.9165→0.9076、C 0.9189→0.9091）。
   也就是说 sign 的下降约一半是弃权变多、一半是方向判断真的变差。
3. **规模的钱应该继续花在 process 头，不是 Move。**
   endpoint 的 +23% 相对 AUPRC 和 q 的 −10% 相对 MAE 都远超 Move 的千分位收益。

## 7. 边界与遗留

1. **区间是“这批 dev curve 上的”，不是“新反应上的”。** 557 条 curve 是冻结的 dev 集，
   CI 描述的是评估语料内的不确定性，不能外推成对新数据的置信区间。
2. **仍然只有 3 个 seed。** 配对 bootstrap 解决的是“curve 抽样”，不解决“seed 抽样”。
   若要声称 seed 级可重复性，只能加 seed（n≥6 才可能到 p<0.05），或者把结论限定为“逐 seed 同号”。
3. **发现一个 evaluator 既存问题（未修）**：`evaluate_checkpoint` 用 **key-row** 窗口
   （`ptr` 由 `n_keys` 累加）去筛选 **node-row** 偏移的 `pair_index`，窗口外的 pair 会被静默丢弃。
   后果是 sign/SRE 的绝对水平只统计了一个子集（本例 6,142 个 active pair）。
   两档、三臂走的是同一条路径且 active pair 数完全相同，所以**配对差值不受影响**，
   但绝对 sign 数值偏低，建议后续单独修并重发 dev 指标。
4. **bundle 的 `model_card.md` 体积 797 KB**，其中绝大部分是 exporter 原样嵌入的 `metrics.json`
   （含 `train_curves` / `dev_curves` id 列表）。这是 20k bundle 就有的既有格式，未改；
   若要发布，建议在 exporter 里裁掉 curve id 列表。
5. **未做**：50k 的闭环评估（rollouts、mis-stop 在闭环上的复算）与 50k confirm 集评估（confirm 仍未读）。
